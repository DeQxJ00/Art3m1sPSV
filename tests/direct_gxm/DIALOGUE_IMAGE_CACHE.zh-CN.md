## 现场证据

录像：`Z:/Record/OBS/2026-09-20 03-56-09.mp4`。
原始实机日志：`build/hardware-logs/20260920-035822-companion/host.log`。

- 当时总缓存只有约 58–60 MiB，低于 192 MiB 总限制。并非单纯总内存不足，也不能把这些长帧归因于 shader 执行。
- 另有仅换句时约 40–50 ms 的帧，主要时间在逻辑阶段。本轮缓存修复不能证明这类长帧已全部消失。

## 最终策略

1. 保持 320 MiB 堆请求及 192 MiB 图片总缓存。闲置池上限从 32 改为 64 MiB，其中闲置 GPU 纹理仍最多 32 MiB。
2. 优先保留预载／CPU 上传时已经存在的像素，备份与已解码闲置像素合计按 32 MiB 进行准入。备份即使对应 GPU 纹理仍在显示，也计入总预算，压力回收可独立丢弃 CPU 备份。
3. GPU 纹理退出时转移已有 CPU 缓冲所有权，之后命中只需上传，不重新读取或解码；同时复用压缩后备中的透明度证书，避免上传时重扫像素。不从 CDRAM 复制像素回来，不增加图像解码线程。
4. 真正因容量不足被拒绝的预载保留所需字节数；消费／解绑释放空间后，按原票据次序补载。一次只补一个，不新建无限队列，不抢占已完成的首用资源，不重新申请章节的 5/6 预留空间。不存在文件、取消、解绑及已转入前台读取的请求不会补载。
5. 冷加载直接解码进 GPU 的图片没有现成 CPU 缓冲，仍使用原压缩后备／淘汰路径；不能承诺所有再次出现的图片都命中解码缓存。

曾测试“GPU 淘汰时复制到 RAM”，实机 960×540 回读约 100 ms；已撤掉，未作为最终优化保留。其对照日志保存在 `build/dialogue-stall-20260920/device-slow-spill/`。
