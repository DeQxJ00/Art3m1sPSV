## 观察

1. n=0 和 n=1 均使用同一张 1×1 已认证不透明纹理，覆盖完整 960×544，alpha=1、普通混合、无裁剪/rule。前者为宿主深色底，后者为黑底。二者连续提交，第二张完全覆盖第一张。第一遍没有可见贡献，可在尚未提交的批次里消除；必须确保没有改变已提交顶点的生命周期。
2. n=4 是 1920×1080 背景，显示坐标为 (-480,-272) 到 (1440,816)，整屏可见。其 alpha bounds 覆盖整张图，但 `opaque=false`。这表示未获不透明认证，不证明它实际有透明像素。`texture_opacity.hpp` 对超过 1024 像素的可选全扫描主动跳过，原因是历史实机扫描造成 12–15 ms 峰值。不能直接提高限额重新引入换句卡顿。
3. n=5/6 为 1020×1008、384×345，n=7/8 为 684×879、330×210 的大人物/附加图块；n=12 是 210×195 头像。它们的包围盒几乎覆盖整张资源，现有整矩形 alpha trim 对它们帮助有限。没有对像素做采样，不能凭包围盒量化透明空洞占比。
4. n=9 的 960×540 纹理覆盖完整屏幕，结合画面可疑为放射线层，但缺少资源名称关联，尚不能当作确认。保持绘制顺序与内容。
5. n=10 为透明度约 0.698 的 960×132 对话框，不能当作不透明覆盖去掉后方图层。

记录中的面积是屏幕内包围矩形面积，不是实测 fragment 数量。模拟器帧率不能用来证明实机收益。

## 后续实施约束

先用独立开关验证尚未提交批次中的全屏不透明覆盖剔除；普通透明、加法、rule、部分裁剪、旋转非满屏、非有限输入均须保持保守路径。保持 shader 字节码、实机 333 MHz 和同步等待不变。通过几何/混合等价测试、模拟器同画面 A/B 后再部署实机。

另查 CPU 整页重建：当前 core 的 `render_gxm.rs` 将等待图标状态变化并入 `frame_visual_dirty`，dirty 或纹理版本变化会走整个 `build_bound_scene`。这说明局部变化可以触发整页重建，不意味着等待图标函数每帧必定返回 true；该页实际失效来源仍需独立量化。
