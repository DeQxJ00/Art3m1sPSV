# 以引擎 Rev.3257 为主的指令移植评估

日期：2026-09-14。主参考为 Toshiue_Kanojo2 内嵌 Windows x64 引擎，otomeriron Rev.3144 用于旧版对照和回归。没有启动 Toshiue EXE。以下保留评估时的缺口说明；2026-09-15 已完成的指令、实现边界及独立验收包见 [移植验收记录](NATIVE_COMMAND_ACCEPTANCE.zh-CN.md)。

注册表、二进制标识、脚本解析范围见 [原生审计](NATIVE_SCRIPT_COMPAT.zh-CN.md)，此次补查的地址、别名断言及原始证据摘要见 [portability.json](evidence/native-script-20260914/portability.json)。本页区分“新版新增”“当前移植版缺项”“原脚本变化”，避免把它们混为同一种兼容问题。

## 真正新增的注册项

| 项目 | Toshiue 的用途与证据 | PSV 处理建议 |
|---|---|---|
| `indentmodify` | 修改当前消息层的缩进栈。`unindent > 0` 弹出指定层数，负数清空，0 不修改；Toshiue 有 6 处 `-1` 调用，清姓名/正文/副语言及分页时使用 | 可以移植，优先。需要文本状态、布局重建和存档回放一起支持，不能仅注册一个空处理函数 |
| `appreview` | 此 Windows 构建注册到空函数，没有可观察的评价/商店操作 | 可按该构建做显式空操作兼容。其他平台真实商店行为没有证据，不伪造执行成功 |
| Lua `getWindowHandle()` | 取窗口对象的原生句柄并转换为字符串；脚本中的相关调用已注释 | PSV 无对应 Windows 句柄，不移植实际功能。若将来需要占位接口，先确认调用者如何判断不可用，不返回伪造句柄 |

以上是注册名称差异：标签 151→153，Lua 注册项 53→54。相同名称不保证所有内部行为逐字相同。此次补查了 `indent/rp/chgmsg/font/wordparts/lyshader/video/trans` 的入口，没有据此宣布全部 151 个同名标签完全等价。

## 已存在的指令：当前移植版还缺什么

| 项目 | 做什么 | 当前缺口、移植难度与建议 |
|---|---|---|
| `indent` 的 `logicalrange` | 决定有限 `range` 如何跨关联显示行累计。开启时，原生会沿行关联标记向前累计计数；从排版用途解释，是按逻辑行处理自动折行后的识别范围 | 两款原生都已有，非 Toshiue 新增。当前 core 没接收此参数，可以补；须区分显式换行与自动折行，不能只保存布尔值 |
| `indent range=0` | 原生 0 表示不限制缩进起始字符的识别范围 | 当前 core 的 `Some(0)` 进入 `chars_in_line < 0`，导致完全不识别；这是可明确修正的语义差异。原生缺省也为 0，当前 core 缺省 None 已表示不限，因此主要差异是显式传 0 |
| `animedel` | 在两版原生注册表中均与 `lydel` 共用处理函数；沿目标删除流程处理，并清理相关记录 | 可优先按 `LydelHandler` 别名补齐。当前 core 已有删除图层事件。需测试目标集合、动画清理、回放一致性；不是另写一套仅清动画记录的功能 |
| `linkreset` | 两版均与 `linkenable` 共用处理函数；Toshiue 最终遍历当前文本层链接对象，调用各对象的复位/启用接口 | 可优先复用 `LinkEnableHandler`，检查禁用→恢复、悬停/点击状态。不是清空文本或删除所有链接 |
| `backloglayer` | 引擎内建的历史文本显示容器：写入、绑定、清空、页数/页偏移/显示页范围/滚动上限查询、上下间距与注释 | 可以移植，但工作量较大，需要历史页数据与文本布局接口。当前游戏主要使用 Lua backlog，未发现直接调用，后排；不必替换现在已工作的 backlog UI |
| `lysave` | 将指定图层对应的表面导出图片，读取 id/file，缺省扩展名为 PNG | 可以移植，需要 core 发出图层导出请求、宿主取得正确表面、完成 GPU 同步后编码保存。应复用现有 PNG/截图基础，但不能把任意图层导出等同于全屏截图；按需执行，不进入每帧路径 |
| `ime` | 文本输入框，含 type、varname、default、位置/尺寸参数 | 可以用 PSV 输入界面适配，但需新增输入请求、确认/取消及变量写回流程。Windows 窗口位置与外观不能直接照搬；当前未发现调用，后排 |
| `unison` | 文件/存档网络同步。下层有信息查询、上传、下载，参数含 server、appname、id、pass、file | 技术上可重做，但依赖服务器协议、返回格式与本地文件规则，不是本地引擎兼容的优先项；当前未发现调用，不启用或发网络请求 |
| `trophy` | 平台奖杯相关入口；这两个 Windows EXE 中为空函数，游戏 Lua 按平台分支调用 | 可以处理不支持平台的兼容分支；不能拿 Windows 空函数当成 PSV 奖杯实现。真实奖杯功能需对应平台证据与资源，暂不承诺 |

`animedel`、`linkreset` 是此次补查修正：此前仅依据其中一段状态清理代码解释用途不完整。注册同一处理函数是更直接的兼容证据，但别名回归仍需验证当前 core 对原有入口的实现。

### 排版依据与实际影响范围

- Toshiue `indent` 入口：`0x1400D7FC0`；当前文本层虚表 +384 → `0x140153760`，保存 range、logicalrange、nest。
- Toshiue 排版消费点：`0x14019CC70`。range 为 0 直接跳过范围限制；非零时才根据 logicalrange 决定是否沿前行累计计数。
- Toshiue 配置：`system/table/list_windows_ja.tbl:399,408` 实际写 `logicalrange=1`；`system/image/boot.lua:710–720` 把该参数传入 `indent`。
- otomeriron 的各语言 `list_windows_*.tbl` 同样有 `logicalrange=1`，因此要作为兼容回归用例。
- 上述 Toshiue 配置未显式设置非零 range。不能仅凭 logicalrange 被忽略就断言当前画面一定排错；必须用有限 range 的测试区分行为。
- `indentmodify` 的当前层状态不能简单变成全局变量，也不能为每次重排无条件清空，否则可能影响嵌套对话。应通过布局状态或可回放的排版指令维护它。

## Lua 接口的可移植性

| 接口 | 已确认用途 | 建议 |
|---|---|---|
| `saveToMemory` / `loadFromMemory` | 把引擎状态序列化为内存字符串，再从字符串恢复 | 可以移植，中等工作量。复用当前状态保存/恢复逻辑，增加内存载体；不临时写文件来冒充，也不承诺读原版 Windows 的内存存档格式。需要脚本位置、层状态、变量、文本和恢复调度一致性测试 |
| `setHttpResponse` | 写入内嵌 HTTP 响应状态 | 可适配，但需先有对应请求/响应生命周期。无实际调用，暂缓 |
| `setUseGlobalCapture` | 原生检查一个布尔参数并写入全局 capture 标志 | 设置入口已确认，标志的完整消费链尚未跟完。不能凭名字当成游戏截图或 OGV 捕获开关；暂不照搬 |
| `dumpMemoryStatus` | 此构建只记录该方法调用并返回空值，未见统计内存的实现 | 如需诊断，可另接现有内存账本；那属于新增诊断能力，不是从此 EXE 得到的统计算法 |
| `initNis` | Windows 图像缩放相关初始化；脚本有 Windows 与 feature level 判断 | 不直接移植 Windows 后端。PSV 维持正确能力判断；将来若需要等效缩放，应独立适配 GXM，不影响已验收 shader |
| `callOeAPI` | 当前脚本用于 Switch 截图、录像、水印，受 `game.sw` 分支约束 | PSV 不执行 Switch API。保留平台分支，当前无需实现真实功能 |
| `getEmoteVersion` | 脚本只在 Emote 变体能力开启时查询 | 此 Toshiue EXE 也未注册，不属于本版新增 API。没有相应实现时不能宣称支持 Emote |

方法有注册、能返回一个值，不等于底层功能已完成。上述无直接调用的接口先保留证据，不在本轮扩大宿主系统功能。

## 脚本和缓存上的变化

Toshiue 的 `cache.lua` 比 otomeriron 更明确地区分了路径展开、去重和执行方式：

| 变化 | 用途 | 能否采用 |
|---|---|---|
| `<auto>` 路径可展开为多张资源 | 覆盖一组 UI 图片，而不是只预备一个文件 | 可以借鉴；Toshiue 自带此 Lua 逻辑，应先让解释器正确执行，避免宿主再展开一次导致重复 |
| `cacheTemp` + `cacheExec` | 一批操作内按路径去重，执行 async/bind/del | 可以借鉴。注册/释放需要对称；去重不等于随意丢弃绑定引用计数 |
| system UI 异步、title UI 同步 | 分开预加载界面资源和需要立即使用的资源 | 作为行为参考。不要改成主线程无限等待，也不把同步标题绑定扩展到每次正文换句 |
| 清加载队列→逆序 unbind→清脚本缓存表 | 先取消未完成的排队工作，再解除本批路径的绑定 | 可以用于核对现有异步流程；不能将清队列直接实现为清空全部 GPU/解码缓存 |
| `isLoadingSurface(path/nil)` 两类查询 | 查询指定路径或总体加载状态，驱动脚本等待恢复 | 必须保持完成、取消、失败可结束等待。此前快进卡死说明需要专项用例，不能只换成“原生同名接口”就算修好 |

原生管理器的已绑定表与可复用表可共享同一 surface 引用，队列对重复路径去重；这可指导生命周期设计，但不证明 Windows 与 PSV 有同一种 GPU 内存布局。`cachemax=400` 是脚本文件数额度，不能直接照搬为 PSV 的 400 MiB 或 400 张满尺寸纹理。

Toshiue AST 的 `rt2/fg/vo/extrans` 等大多是游戏 Lua 层命令，不是应该逐一增加的低层 native tag。Switch 分支中的 `val` 两版原生都没有注册，疑似脚本拼写问题，不能擅自扩充一个新命令。

## 建议实施顺序与验收

1. **文本兼容组**：`indentmodify`、`indent logicalrange`、显式 `range=0`。测试嵌套括号、自动折行/显式换行、姓名与正文独立状态、翻页、backlog 返回及保存恢复；再用 otomeriron 作为旧版回归。
2. **小型别名组**：`animedel`、`linkreset`，以及本 Windows 构建明确无操作的 `appreview` 兼容。测试与已有入口在相同初始状态下产生一致结果。
3. **现有加载接口组**：针对重复 bind、队列取消、unbind、失败完成、快进、退出游戏做离线用例，然后才改实现和实机验证。保持既有缓存额度，不与排版改动合成一个难定位的包。
4. **按真实使用再补**：`saveToMemory/loadFromMemory`、`lysave`、`backloglayer`、`ime`。有可用实现路径，但目前没有证据证明这两款游戏必须调用它们。
5. **暂不实现实际功能**：Windows 窗口/NIS、Switch 系统接口、远程同步及缺少消费链证据的 capture 标志。

这些工作主要提高脚本兼容性和行为一致性。不能承诺补完几个标签就提高帧率；每帧渲染、解码和缓存压力仍需独立测量。本轮没有调整 shader、音视频解码或内存额度。
