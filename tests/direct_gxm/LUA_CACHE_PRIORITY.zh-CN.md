# 游戏 Lua 优先的图片预载候选

## 问题与调整

游戏原有 `system/image/cache.lua` 已经通过 `bindSurfaceAsync` 提交背景、人物身体、表情和头像。旧加载器以遮罩、动画、普通、普通四个机会轮转，补充效果请求在共享额度紧张时还能降级普通图片的解码结果。因此游戏已提前准备的图片可能在首次显示前退回压缩源。

本候选基于主仓库 f07f47e / 核心 0b8ae9c，沿用实际游戏 Lua，不修改或替换商业游戏脚本：

- 即时显示需求仍优先；正在执行的解码不被强行中断。
- 有脚本绑定引用的预载优先，按首次 Lua 绑定顺序选择。顺序与用于取消校验的加载 ticket 分开，章节先提交、后来才被 Lua 绑定的资源也保持正确顺序，不重启其正在执行的加载。
- 双方都有任务时，最多连续处理四个脚本请求，然后给一个补充预载机会；补充遮罩、动画、普通提示轮转。它是任务数量比例，不是耗时比例。没有脚本请求时补充预载正常连续执行。
- 排队容量仍为 64。新 Lua 请求可从已有延期记录中优先选出，不必等满队列的补充任务全部完成。
- 补充预载不再回收尚有脚本绑定的首次使用解码结果。脚本预载需要空间时，可以降级无脚本绑定的补充像素，保留其压缩源；优先从较晚提交的补充资源回收。
- 容量不足后的补填同样优先 Lua 绑定顺序。既有前台需求、类别容量和取消协议不变。

这不是准确的“下一句距离”预测：接口只有路径，没有使用句号。不会为遮罩固定分配 VMEM，也不增加 GPU 预上传。320 MiB 堆、192 MiB 共享缓存、32 MiB 闲置 GPU 上限，以及 16/32 MiB 遮罩/动画子额度保持不变。GPU 上传失败回收修复继续保留。

## 本地验证

538 项核心测试通过，18 项忽略。新增验证包括：补充队列已满时 Lua 请求优先且补充任务仍有进度、章节资源后绑定只加载一次且遵循 Lua 顺序、补充遮罩/动画不能降级已绑定像素、Lua 预载可借用无绑定补充像素但保留压缩源、容量补填优先 Lua 顺序。已有即时需求、预算记账、取消、换章和上传压力测试全部通过。

证据：`build/lua-cache-priority-full-tests.log`、`build/lua-cache-priority-vita-build.log`、`build/lua-cache-priority-host-build.log`。启动日志标记为 `priority=lua-first-v1 script_burst=4 protect_bound_pixels=1`。

## 实机验收

先验证启动像素自检。实际游戏保持 333 MHz，比较同一段首次进入的背景/立绘和灰度情景切换，再检查首次遮罩/放射动画切入是否退步；最后连续换句、快进、换章并读档，确认没有卡死或人物缺层。

需区分 Pixels / Encoded 缓存命中、需求等待、GPU 上传失败与绘制耗时。启动通过不能代替性能验收；原人物缺层问题仍是暂未复现、尚未充分验收。本文件建立时尚未完成本候选的实机性能验证。
