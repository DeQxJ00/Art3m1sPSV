# 源码目录与命名整理方案

状态：2026-09-21 调查后提出的迁移方案；尚未搬移运行源码或更改构建行为。

## 已确认的问题

- 正式构建脚本读取 `build/heap-audit/controls-source/core`，该目录是另一 Git 工作区中的核心源码；根目录 `core/` 与它分开维护。正式源码不应依赖被忽略的临时构建目录。
- 根目录宿主与内部核心仓库分开提交，根目录通过 `patches/` 保存部分核心变更。应先明确当前核心版本及差异，不能直接把两个目录相互覆盖或假定按文件名应用补丁就能恢复完整版本。
- `host-direct/` 是当前 GXM 宿主；它仍编译 `host/` 的文件、音频、视频模块，并使用其中的字体资源。`host/` 不能整体删除。
- 当前构建脚本写死开发机、工具链路径；默认 CMake 核心库和部分构建文档仍指向旧基线。
- 游戏名称出现在补丁、脚本、报告、注释、shader 标识与生成代码中；主菜单还有按具体游戏编号排序的逻辑。
- `tests/` 同时放可执行测试、历史实机报告和研究证据；根目录也混有早期规划及过期状态说明。

## 建议目标目录

```text
README.zh-CN.md                 当前功能与唯一推荐构建入口
core/                          正式 Rust 核心及其 crates
host/
  vita/                        当前 Direct GXM 宿主、菜单及平台桥接
  media/                       音频、视频及相关队列和转换代码
  platform/                    文件 IO、线程亲和性等平台支持
assets/
  fonts/                       菜单字体、许可证
  demos/                       内置与外置 shader 演示资源
shaders/
  renderer/                    基础绘制、字体、视频转换
  effects/                     按算法命名的内置效果
generated/                     可重现的 shader 头、菜单字形等生成文件
tests/                         自动化测试与合成测试数据，保留功能子目录
tools/
  build/                       统一编译、shader 生成和打包入口
  deploy/                      安装、连接、日志采集
  diagnostics/                 性能分析和调试工具
  assets/                      通用资源处理工具
docs/
  architecture/                渲染、缓存、加载、脚本、音视频设计
  build/                       工具链、构建与发布步骤
  testing/                     测试方法及匿名验收记录
  history/                     旧基线与已结束实验记录
vendor/                        实际依赖的第三方源码与许可证
local/                         忽略：本机路径、样本映射和原始研究证据
build/                         忽略：所有中间产物、日志与发布包
```

`generated/` 中运行构建必需的产物是否提交，按生成工具可获得性决定。不能因为是生成文件就删除当前构建所需的已验证 GXP 或头文件；需要同时记录生成输入、命令和工具版本。

## 去游戏名规则

1. 正式源码、文件名、shader 标识、注释和文档使用功能名称，例如 `font_roles`、`dialogue_reveal`、`portrait_composition`。不能只把名称替换成编号、继续保留按游戏名分支的逻辑。
2. 测试使用 `sample_01` 等中性编号。真实名称、安装路径、资源提取位置与样本映射进入不提交的本地清单；公开提供不含真实名称的配置模板。
3. 游戏列表名称从用户资源的标题信息读取；排序按通用规则或用户配置，移除写死的具体游戏排序名单。用户自己提供的标题仍可正常显示。
4. 兼容行为优先根据脚本字段、引擎能力、资源结构或内容签名选择，不根据目录名或游戏简称。确有必要的例外使用描述行为的配置项，并保持默认语义清楚。
5. shader 改名要同时更新注册表、生成器、演示清单和引用。游戏资源要求的 shader 查找键不能任意修改；确认哪些是内部名称，哪些属于外部文件接口后分别处理。
6. 不改变用户已有游戏目录、存档标识和缓存路径。源码匿名化不应使已有存档或 shader 缓存失效。
7. 不改第三方许可证、作者归属或普通技术术语。名称检查使用经过审查的明确词表，不能全仓库盲目替换短词。
8. 原始日志、反编译输入、真实资源和视频留在本地。历史报告若需保留到源码仓库，应另做匿名摘要，不能将原始证据改写后继续声称是原件。

## 分批实施与验收

### 第一批：统一正式核心和构建入口

- 记录外层与核心仓库提交、工作区差异，以及最后可用包的身份；保留原工作区作为回退来源。
- 推荐将已验证的核心版本纳入根仓库 `core/`，以后宿主和核心用同一个提交描述；不将内部整份项目副本复制进来。
- 比较并保留根目录核心中尚未合入的有效内容，确认 Cargo 路径依赖与生成文件完整后再迁移。
- 构建脚本从脚本位置确定项目根目录，通过环境变量或本地配置获取工具链；默认入口重新编译当前核心，避免静默链接旧静态库。
- 检查现有独立补丁是否已合入；已合入的转入历史记录，未合入的明确标注用途。第三方构建补丁继续保留。
- 验收：在新的干净检出中，仅配置声明的工具链与依赖即可运行测试、重建 VPK；不依赖原 `build/` 中的源码或基线库。

### 第二批：模块归位

- 搬移宿主、媒体、资源、工具及文档；同步修正 CMake、Cargo、资源打包和脚本引用。
- 构建依赖确认后再移除不再使用的旧模块和第三方库；旧版本源码仍可通过 Git 历史查阅。
- 这批只改变组织方式，不同时修改 shader 算法、内存额度、资源调度或同步逻辑。
- 验收：核心和宿主相关测试、VPK 内容清单、shader 自检以及真机启动、对话、菜单、存读档、视频与 OGV 冒烟测试。

### 第三批：匿名化和防回归

- 把游戏专属工具改为接受样本配置或资源路径的通用工具；测试名称改为所验证的行为。
- 处理文件名、正文、生成数据和打包演示中的名称；检查生成源，避免重新生成后把旧名称带回来。
- 添加源码与包内容检查，明确第三方术语豁免项；不扫描用户运行时资源来强制去名称。
- 验收：正式源码和演示不含明确游戏名称、简称与硬编码游戏编号；匿名样本配置可运行，已有资源和存档仍可使用。

## 历史边界

以上清理针对整理后的源码与发布包，不会自动移除 Git 历史中的旧名称。现有标签和验收提交应继续保留。若以后发布时要求整个仓库历史也不含名称，另行生成经过检查的干净源码快照或发布仓库，不在这次目录整理中重写开发历史。
